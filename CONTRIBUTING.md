# Contributing

Thanks for looking. Grapevine is small and opinionated about one thing: every
number it publishes has to trace to something you can re-run. Most of the rules
below follow from that.

## The rules that are not negotiable

These are in [`CLAUDE.md`](CLAUDE.md), which applies to anyone working in the
repository, human or model. In short:

- **No number without a run.** A quantitative claim in a committed file traces
  to a committed run or to a deterministic computation in the repository.
  Something not yet produced is written `not run`.
- **Synthetic data never becomes a result.** Scripted or mocked episodes carry
  `synthetic: true`, and a results table containing one must fail to build.
- **No training claims without training.**
- **Pre-register before any paid run**, in `docs/prereg/`, with the analysis
  script committed first.
- **Bad results ship.** Do not delete, overwrite or rerun a committed result
  because of how it came out.
- **Committed runs are immutable**, and so are the generators they depend on.
  Changing an environment means a new family name.
- **Citations are verified or marked `UNVERIFIED`.**

## Setting up

```bash
uv sync --extra dev                 # core and tests
uv sync --extra dev --extra rl      # plus GRPO (pulls torch)
uv sync --extra dev --extra docs    # plus the docs site
```

## Before you open a pull request

```bash
uv run pytest -q
uv run ruff check grapevine tests studies examples
uv run mypy
uv run mkdocs build --strict        # if you touched docs/
```

All four must pass. Also:

- Public API changes update `grapevine/__init__.py`'s `__all__`, the API page in
  `docs/`, and `CHANGELOG.md` in the same pull request.
- Public functions and classes have Google-style docstrings with types.
- Generated tables and figures are regenerated by their script, never edited by
  hand inside their markers.
- If you code against an external library, read its current documentation,
  note the version you read, and pin to it.

## Adding a check to the battery

A check is only as good as its calibration. A new check comes with:

1. a planted-flaw fixture in `tests/fixtures/flawed_envs/` that it catches;
2. a test that the clean control still passes every check;
3. its row in `docs/audit-battery.md`, with the finding it comes from.

If the new check fails an environment that has committed runs, the
environment's generator does not change. Its card is regenerated and the
failure stays on it, as `hidden_profile_v2`'s does.

## Adding an environment

Implement `grapevine.Environment` (see `examples/02_write_an_environment.py`),
commit its Validity Card next to it, and say in the pull request which checks it
fails and why that is acceptable, if any.

## Reporting a problem

Open an issue. For a flaw in an environment or a check, the most useful report
is a seed and the command that shows it. For a security issue, see
[`SECURITY.md`](SECURITY.md).
