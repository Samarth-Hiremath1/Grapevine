# v0.2 plan

*Written 2026-11-15, at the start of the v0.2 branch. Scope and non-goals are
fixed here so the release stays finishable.*

## What v0.2 ships

Grapevine checks whether a multi-agent eval or RL environment measures
coordination or something else, and gives you environments and GRPO wiring that
pass that check.

1. `grapevine audit <env>` — an offline, no-key validity checker for
   distributed-information environments and their rewards, calibrated against
   environments with planted flaws.
2. `hidden_profile_v2` — one environment that passes the audit, with its
   Validity Card committed.
3. `grapevine.rl` — GRPO wiring (TRL) with provably frozen partners and an
   audit gate. Scaffolding, smoke-tested, **no training results.**
4. The v0 underspecification case study as the worked example of why the audit
   exists.
5. Real packaging: installable, typed, documented, examples run in CI, every
   number machine-checked.
6. One small pre-registered multi-model eval run — **only if keys and budget
   allow** (see Blockers).

Non-goals, to be listed in the README under "Roadmap (not in this release)"
without dates: real training runs, GPU jobs, a new RL algorithm, adapters for
external benchmarks, Inspect or OpenEnv integration, privacy or
disclosure-constraint environments, communication-budget / routing /
counterfactual-replay machinery, and any claim about another benchmark's
results.

## External APIs, fetched 2026-11-15

Nothing below is from memory. Each was read from the live documentation on

### TRL — usable, but the wiring must be retargeted

- PyPI latest **1.18.0**; `uv.lock` currently pins **1.13.0**; `pyproject.toml`
  declares `trl>=0.11`, which is seven major versions stale and is what the
  existing `grapevine/train/` was written against. Pin properly in v0.2.
- Read: `https://huggingface.co/docs/trl/v1.18.0/en/grpo_trainer`.
- `GRPOTrainer(model, reward_funcs, args, train_dataset, eval_dataset,
  processing_class, reward_processing_classes, callbacks, optimizers,
  quantization_config, peft_config, tools, rollout_func, environment_factory)`.
- A reward function is called with `prompts`, `completions`, `completion_ids`,
  `trainer_state`, `log_extra(column, values)`, `log_metric(name, value)`,
  `environments` (only with `environment_factory`), **and every dataset column
  except `prompt`, by name**. It returns `list[float]`, and may return `None`
  for samples it does not apply to. `**kwargs` in the signature is the
  documented way to stay compatible. Sync or `async def` both work; multiple
  async reward functions run under `asyncio.gather`.
- `GRPOConfig` defaults that matter: `num_generations=8`,
  `per_device_train_batch_size=8` (effective batch must be divisible by
  `num_generations`), `max_completion_length=512`, `beta=0.0` (**no reference
  model is loaded at 0.0**), `loss_type="dapo"`, `scale_rewards="group"`,
  `use_vllm=False`, `remove_unused_columns=False`, and `use_cpu` exists for the
  CPU smoke config. `processing_class` must pad on the left.
- LoRA is `peft_config: PeftConfig` (PyPI `peft` latest **0.21.3**), or pass an
  already-wrapped `PeftModel` as `model`.
- `environment_factory` is **not** a multi-agent hook: it is one stateful
  environment instance per completion whose public methods are exposed to the
  policy as tools (`reset()` required, `get_reward()` optional, needs
  `transformers>=5.2.0`, marked experimental). It does not fit a team of agents
  taking turns.
- **Confirmed against the installed 1.18.0 source in Step 5:** the reward call
  passes every dataset column except `prompt` by name, plus `trainer_state`,
  `log_extra` and `log_metric`; sync reward functions run on the main thread and
  async ones on a separate loop thread. `max_prompt_length` is gone from
  `GRPOConfig`; `report_to` defaults to `"none"`.
- `rollout_func(prompts, trainer) -> {"prompt_ids", "completion_ids",
  "logprobs", ...}` is the only hook that would let one policy generate every
  agent's turn in a real episode, and it makes us responsible for generation
  and logprobs. Also experimental. *Planned* for self-play; **changed in Step
  5** — see `docs/decisions.md` — self-play is a plain reward function too. Extra keys returned by `rollout_func` are forwarded to reward
  functions, which is how role and turn tags will reach per-role grouping.

### `verifiers` — recommend skipping, roadmap instead

- PyPI latest release is **0.4.1**. The v1 API in the Prime Intellect docs is a
  *different* library generation: `class MyEnv(vf.Env[MyConfig])` with
  `async def run(self, task: vf.Task, agents: vf.Agents) -> None` and
  `async def finalize(self, task, episode) -> None`, per-role
  `vf.AgentConfig` fields on an `EnvConfig` subclass (`--env.solver.model`),
  `agents.<role>.trainable = False` to freeze a helper role, harnesses,
  toolsets installed as MCP servers, and episodes assembled from per-agent
  traces.
- Read: `verifiers/overview.md`, `verifiers/env.md`,
  `verifiers/getting_started.md` under `https://docs.primeintellect.ai/`.
- Multi-agent with per-role models and a `trainable` flag is exactly the shape
  Grapevine wants. But the documented install is `git clone
  PrimeIntellect-ai/verifiers && uv sync`, not a released PyPI version; the
  local commands are `uv run vf-run <env>` / `uv run vf-validate <env>` from
  inside that clone, full evals go through `prime-rl`'s `uv run eval`, and
  Harbor tasksets need Python 3.12+. The minimal taskset package layout is not
  specified on the pages that describe it.
- That is an unpinnable git dependency plus a second CLI toolchain, which fails
  the "small, clean wrapper" test in the plan. **Recommendation: do not build
  the adapter in v0.2.** Put "`verifiers` v1 multi-agent adapter (per-role
  `AgentConfig`, non-trainable helper roles)" in the roadmap and revisit when
  v1 is released to PyPI. *Needs Samarth's sign-off before I act on it.*

## Public API draft

One import surface, everything else underscore-private. `__all__` in
`grapevine/__init__.py`:

```python
# The protocol outside users implement. Small and intended to stay stable.
"DistributedTask",      # a single task: per-agent views, objective, answer space, score()
"Environment",          # deterministic generate(seed), train/eval seed splits
"ScoreResult",          # score(answer) -> correct, plus per-check detail
"AgentView",            # one agent's view: shared units, private units, rendered text

# Registry, so `grapevine audit <name>` and configs can name an environment.
"register_environment", "get_environment", "list_environments",

# Bundled environments.
"HiddenProfileV2", "HiddenProfileV2Config",

# The audit battery.
"audit",                # audit(env, n_tasks=..., seed=...) -> ValidityCard
"ValidityCard",         # to_json() / to_markdown(); hashable for manifests
"Check", "CheckResult", "Severity",

"__version__",
```

`DistributedTask` adds to today's `Task`: an explicit `objective` (question
*and* scoring rule, stated by default), a programmatic `score(answer) ->
ScoreResult` so the audit never needs a model to know what is correct, a
`full_view()` for the full-information baseline, and `required_units` replacing
`required_private_facts` (units, not sentences, so minimality is checkable).
`Environment` adds `train_seeds()` / `eval_seeds()` so an RL user cannot train
on eval tasks by accident.

`Task` and `Env` stay as aliases through v0.2 — the committed v0 runs load
through them — and are documented as deprecated in `CHANGELOG.md`.

`grapevine.rl` lives behind an optional `[rl]` extra so the core install stays
light (httpx, pyyaml, rich, numpy, python-dotenv, matplotlib). It is not
exported from the top-level package.

CLI: `grapevine audit <env>` (the headline), `grapevine eval --policy <path>`,
`grapevine verify-claims`, and the existing `view` / `gen` / `metrics`.
`grapevine diagnose` is folded into `audit` as the reward-hackability check and
kept as a hidden alias for one release.
