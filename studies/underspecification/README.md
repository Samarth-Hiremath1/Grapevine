# Study: a coordination failure that was objective underspecification

This is the experiment Grapevine's audit tool came out of. It is kept here, in
full, because the mistake is the point: the first version of this result was
published with a headline that the evidence did not support, and what caught it
was that every number traced to a committed run.

**One command reproduces every number below. No API key, no network.**

```bash
uv run python -m studies.underspecification.reproduce
```

## The question and what happened

Three LLM agents hold the facts needed for a hiring decision between them. The
facts every agent shares favour a decoy candidate; the facts that make the
right candidate correct are split one cluster per agent, and the right answer
only wins once all of them are on the table. That is the hidden-profile
structure (Stasser & Titus, 1985), which HiddenBench (arXiv:2505.11556) studies
in LLM groups.

| Condition | Task not stated | Task and rule stated |
|---|---|---|
| A. one agent, all facts | 171/200 · 85.5% | original prompt 96/100 · 96%<br>matched prompt 100/100 · 100% |
| B. three agents, no talking | 1/200 · 0.5% | 0/100 · 0% |
| C. three agents, told to share | 134/200 · 67.0% | 100/100 · 100% |
| D. three agents, neutral prompt | 111/200 · 55.5% | 99/100 · 99% |

Chance is 25%. These cells are regenerated by the command above, not typed in.

**B is the robust result.** With no communication every agent sees the decoy
ahead in its own facts and votes for it, whether or not the task is stated.

**The gap I first reported as a coordination failure was not one.** Agents
shared every required fact in 200 of 200 C episodes and still trailed A by 18.5
points, which I read as a failure to integrate pooled information. Transcripts
showed agents asking what decision they were supposed to be making, in 174 of
200 C episodes. No prompt in any condition stated the question or the scoring
rule. Adding both took C from 68/100 to 100/100 on the same tasks, and those
requests fell to 2 of 100.

**A second mistake, caught the same way.** With the task stated, C and D first
appeared to beat A (100 and 99 against 96) — which would have been a much more
exciting claim. A's prompt was laid out differently from the other conditions.
Given the same layout, A scored 100/100.

The transferable lesson, and the reason `grapevine audit` exists: an evaluation
that does not tell agents their objective can produce a coordination failure
that looks real — every fact gets shared, the team still chooses wrong — and
vanishes once the objective is stated.

## Reproducing it

```bash
# Rebuild every table and the figure from the committed episodes.
uv run python -m studies.underspecification.reproduce

# Show the paid commands that produced the committed runs, and what each cost.
# Reconstructed from each run's own manifest; it does not run them.
uv run python -m studies.underspecification.reproduce --rerun

# Read one transcript, with each required fact marked by whether and when it surfaced.
uv run grapevine view \
    studies/underspecification/runs/20260913T013826Z_rule_arm/episodes_communication_rule.jsonl
```

Reruns regenerate identical tasks. They do not regenerate identical answers:
`gpt-5.6-luna` rejects an explicit temperature, so every call ran at the model
default of 1.0 (`docs/decisions.md`). A rerun writes a new timestamped
directory and overwrites nothing.


### Why the prompts are frozen

The episodes record what the models said, not what they were asked. Nothing in
the repository would have noticed if a prompt template drifted and these runs
stopped reproducing from the code — and since the finding *is* about a prompt,
that gap mattered more here than usual.

`prompts.py` rebuilds every prompt by calling the same builders the rollout
engine calls, so a reconstruction that drifted from the engine would be a bug in
the engine. `freeze_prompts.py` hashes the result: 14 digests covering all 1,580
committed episodes and 7,260 model calls, plus the readable text for one task.
`tests/test_study_prompts.py` re-derives both on every CI run, and includes a
negative control that edits a template to prove the check can fail.

The same tests assert the study's central claim directly: strip the task
statement from the rule arm's prompts and they are byte-identical to the primary
run's, for all 100 paired tasks. The rule arm changed one thing.

## What the audit says about this environment

`grapevine audit hidden_profile` is run by the reproduce command above and its
card is committed as [`validity_card.md`](validity_card.md). It reports **fail**:
three failures, four warnings, five passes.

The three failures are the reason `hidden_profile_v2` exists:

- `shortcuts` — counting how often each candidate's name appears solves 200 of
  200 tasks, so the task measures whether a model counts, not whether it reasons
  over the facts.
- `objective` — five of the ten conditions never state the question or the
  scoring rule. This is the finding the study is about, found again mechanically.
- `solo_solvability` — every private fact supports the correct option, so an
  agent asking only "whose name is in my own notes?" is right 200 of 200 times
  with no pooling. **The hand audit missed this one**; the battery found it. It
  is written up as A1 in `docs/audit.md` and changes no reported number, but it
  does change what condition B can be read as measuring.

The card is regenerated by the reproduce command and diffed in CI, so if a
change to the battery or the environment moved any of these, it shows up as a
failing build rather than a stale file.

## Limitations

These are the ones that bear on what the study can support. The full list, each
with its numbers, is in `docs/results.md`.

- The task has a trivial shortcut: counting name mentions solves 200 of 200
  full-information contexts. `hidden_profile_v2` exists to remove it.
- All 200 tasks share one support pattern (correct 6, decoy 5, others 1 and 0)
  and the same 12 fact sentences: one puzzle in 200 arrangements, not 200
  problems.
- One model, one task template, three agents, two rounds, four options.
- The surfacing metric has precision 1.00 and recall about 0.86 against 40
  model labels (`docs/audit_surfacing_labels.md`), not human ones; it undercounts paraphrased sharing.
- The rule arm is N=100 against N=200.
- Condition D's 4 parse failures are empty responses, probably from hidden
  reasoning tokens exhausting the output cap. Not confirmed: usage is logged per
  episode, not per call.

The generator behind these runs is frozen (`CLAUDE.md` rule 6). Changing it
would mean the committed episodes no longer regenerate from the code, and any
new arm on the same seeds would no longer be paired with them. Improvements go
into `hidden_profile_v2` instead.
